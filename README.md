# Bulk Certificate Generator

Backend API built with FastAPI. You send a list of recipients in one request and it
generates a PDF certificate for each of them using one fixed template.

## Tech used
- Python 3.10+
- FastAPI
- SQLAlchemy with SQLite (relational db)
- ReportLab (to make the PDFs)
- pytest + httpx for tests

## Setup
```bash
python -m venv venv
source venv/bin/activate        # on Windows: venv\Scripts\activate
pip install -r requirements.txt
```

## Run the app
```bash
uvicorn main:app --reload
```
App runs on http://127.0.0.1:8000. Swagger docs are at http://127.0.0.1:8000/docs
(easy way to try the APIs).

The database file `certificates.db` and the folder `generated_certificates/` are created
automatically on first run.

## Run tests
```bash
pytest
```
Tests use a temporary database and folder so they don't touch the real data.

## API

### 1. Submit a generation request
`POST /jobs`

```bash
curl -X POST http://127.0.0.1:8000/jobs \
  -H "Content-Type: application/json" \
  -d '{
    "course_name": "Python Basics",
    "issue_date": "2026-10-07",
    "recipients": [
      {"name": "Rahul Sharma", "email": "rahul@example.com"},
      {"name": "Priya Das", "email": "priya@example.com"}
    ]
  }'
```
Response (202 Accepted):
```json
{"job_id": 1, "status": "pending", "total": 2}
```

### 2. Check status / progress
`GET /jobs/{job_id}`

```bash
curl http://127.0.0.1:8000/jobs/1
```
Gives the job status (`pending`, `processing`, `completed`), `total`, `success_count`,
`failed_count` and the list of certificates. Every certificate has its own `status`
(`pending`, `success`, `failed`) and an `error` message if it failed.

### 3. Download certificates
- One certificate: `GET /jobs/{job_id}/certificates/{certificate_id}`
  (the `download_url` field in the status response has this path)
- All successful ones as a zip: `GET /jobs/{job_id}/download`

```bash
curl -O -J http://127.0.0.1:8000/jobs/1/download
```

## Design decisions

**Background processing instead of synchronous.**
A request can have hundreds of recipients, and making PDFs one by one takes time. If it was
done inside the request the client would have to wait and could get a timeout. So `POST /jobs`
saves everything in the database, returns `202` right away, and the PDFs are generated by
FastAPI `BackgroundTasks`. The client then polls `GET /jobs/{id}`.
I chose `BackgroundTasks` because it needs no extra setup. The downside is that if the server
restarts while a job is running, that job will stay stuck in `processing`. For production I
would use Celery/RQ with Redis.

**Validation is done per recipient.**
The recipient list is not strictly validated by pydantic, because then one bad recipient
would give a 422 for the whole request. Instead the request-level things (course name,
date, empty list, max 1000 recipients) are checked up front, and each recipient is checked
separately (name required, valid-looking email). Invalid ones are saved with status `failed`
and the reason, and the valid ones still get generated.

**Failure handling.**
Generation of each certificate is inside its own try/except, so if one fails the error is
stored and the loop goes on with the next recipient.

**Storage.**
PDFs are saved on disk in `generated_certificates/job_<id>/` and only the path is stored
in the database.

**Two tables:** `jobs` (course, date, counts, status) and `certificates` (one row per
recipient, with status, file path and error).

## Limitations
- No authentication.
- Max 1000 recipients per request (`MAX_RECIPIENTS` in `main.py`).
- Duplicate recipients are not detected, each row gets its own certificate.
- Jobs are not retried automatically.
